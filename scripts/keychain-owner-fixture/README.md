# Synthetic legacy Keychain ACL observation — unrun design

This is a **disposable GitHub-hosted macOS VM only** fixture. It is not a production recovery tool. Do not execute on a user's Mac, regular account, self-hosted runner, or keychain. `SecKeychainCreate` may add the fixture to the runner's search list or affect its default; only the disposable VM's system state can be affected. The program, shell and Python supervisor each refuse to run unless expected GitHub-hosted runner signals and `runner` account/path are present. These are accident guards, not cryptographic attestation of a VM; an attacker who controls the environment can spoof them. The VM is discarded after the job. Do not upload its keychain, artifacts or logs containing signing inspection output. No real credentials, personal data, Developer ID keys, production app, or live profiles are used.

The shell builds two identical source executables with different basenames and ad-hoc identifiers, verifies them, and invokes them sequentially. The A setup process creates two new explicitly referenced temporary keychains (target and decoy) and one fake item with controlled `SecAccess` trusted-application list for A. B itself seeds its own positive-control item into the target and a decoy-only fake item into the other keychain. Each query is limited to the fake keychain via `kSecMatchSearchList` and matches fixed fake service/account; `SecItemCopyMatching` requests only an item reference, not password data or attributes. The program verifies the returned reference belongs to the fake keychain before calling `SecItemDelete` only on that exact reference via `kSecMatchItemList`. Legacy user interaction is disabled in each process and queries request `kSecUseAuthenticationUIFail`; either can be unsupported by a particular implementation, which is an inconclusive result, not a reason to weaken safeguards.

Before either deletion, the B process inspects the explicitly bounded fake A item and its own fake B control. It requests the DECRYPT ACL list and only interprets its first ACL when the list contains exactly one entry and that entry contains exactly one trusted-app reference. It obtains that reference's data via `SecTrustedApplicationCopyData`, and independently obtains references for A, B and the actual caller. Path-like data is decoded only in memory: length at most `PATH_MAX + 1`, exactly one NUL at the end, valid UTF-8, absolute path and no `://`; trailing slashes are stripped and only a final basename is compared. No path, basename, account, service, description or raw data is printed or written. Per-item output contains only fixed event labels, API OSStatus values and A/B/caller match or shape tri-states (-1 unknown, 0 false, 1 true). A missing or multiple ACL/app, invalid types, malformed/non-path data, missing NUL, overlong buffer, or API failure is inconclusive; the process does not proceed to deletion in that case. Expected controlled observations are A item matching A but not B, B item matching B but not A, and current caller matching B in both. These controls do not assert that securityd uses this exact logic.

B proves that the decoy-only item is absent when searching the target and present when searching the decoy. B then tries to delete A's item, checks it remains, deletes its own item and verifies not found. Finally A deletes A's item and verifies not found. Search and actual delete statuses are reported separately; if delete was not attempted its value is an explicit sentinel. A captures search-list and default snapshots before creation, reports equality/unknown after creation and after the complete attempted sequence, and stores the snapshot only in an owner-only VM-temporary file that is never uploaded. The supervisor applies a 90-second external timeout to each phase and the workflow has a 10-minute timeout. A nonzero exit, unsupported ACL, unexpected owner result, permission failure, or differing statuses is a fixture/setup failure or inconclusive observation. If all previous controls and both complete expected ACL observations pass and an actually attempted `SecItemDelete` returns exactly -25244, this synthetic run observed a result consistent with the hypothesis under the stated conditions. Even a confirmed synthetic match does not establish which code path ran inside securityd. Search failures and all other results are inconclusive, never a reproduction. Both snapshots must have known equality values 0 or 1 (0 is permitted in the disposable VM); an unknown value -1 is inconclusive. The supervisor exits nonzero when the controls or exact status are not obtained; a failed job can mean unsupported fixture conditions, not a product defect. Names, paths, raw keychain attributes and fake values are not printed by the program. System logs are not exported. Paths may appear in CI command failures but only under the disposable runner.

## Expected deployment by the coordinator

1. Review `fixture.m` and `run.sh` (especially guard, explicit keychain, reference check and no user-data inputs). This design has not been reviewed against the exact production call or executed on any Mac.
2. In a separate diagnostic branch, place `fixture.m`, `run.sh`, and `supervise.py` under `scripts/keychain-acl-fixture/`; place `workflow.yml` under `.github/workflows/` under a new workflow name. Preserve existing workflow files. The proposed workflow uses a push trigger only for the exact new branch `codex/neantik-keychain-acl-fixture-20261117` in `AffPapa/neantik`, guarded again in the job; it targets a GitHub-hosted macOS runner, uses no configured secrets, and does not run on PRs, schedules, forks or self-hosted runners. It uses a read-only GitHub token solely for checkout, without persisted credentials. Pin checkout action to its immutable SHA as shown. `persist-credentials: false` prevents leaving checkout credentials in the workspace.
3. A push of the reviewed commit to that exact branch **starts the diagnostic job automatically**; `workflow_dispatch` is intentionally not used because a workflow absent from the default branch may not be dispatchable. Check branch absence and all safety criteria before the one intended push. Confirm the job actually ran the intended commit and used a GitHub-hosted macOS VM. Read status JSON and positive controls, not just conclusion. No fixture source should be installed in the shipping app.
4. Delete no user data or user keychain. A CI observation remains bounded to ad-hoc signatures, this runner OS and synthetic access configuration. It does **not** prove or disprove why the real -25244 occurred, identify the owner of the user's item, authorize changing ACLs, prove identity equivalence to Developer ID, or qualify a release.

## Local verification allowed

`clang -fsyntax-only -fobjc-arc -Werror -Wno-deprecated-declarations fixture.m` performs syntax/type checking without linking or running the program. `bash -n run.sh` checks shell syntax and `python3 -m py_compile supervise.py` checks Python syntax. No Security API may be invoked locally.

Primary references: [Apple Security SecItem implementation](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_keychain/lib/SecItem.cpp), [Apple Keychain operations](https://developer.apple.com/documentation/security/updating-and-deleting-keychain-items), [GitHub-hosted runner isolation](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

## Interpretation boundary

The bounded decoding is an intentionally stricter, safe approximation of Apple open-source `SecItem.cpp` and `SecTrustedApplication.cpp` (which currently compare basename-like trusted-application data in a legacy delete path). The open-source `main` branch is not the exact shipped macOS image and does not prove that the runner uses the same implementation. The code only inspects newly created fake CI items; it never reads the real pending item or its ACL. It does not prove ownership, authorise a user Keychain change, validate Developer ID equivalence, or qualify release.

Reference: [Apple SecItem.cpp](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_keychain/lib/SecItem.cpp) and [SecTrustedApplication.cpp](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_keychain/lib/SecTrustedApplication.cpp).
