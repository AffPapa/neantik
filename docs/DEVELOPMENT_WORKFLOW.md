# Короткий цикл разработки NeAntik

## Обычная правка

1. Прочитать CURRENT/checkpoint и выбрать одну изменяемую поверхность.
2. Получить read-only план через `python3 -B scripts/plan-manager-checks.py --base HEAD`, проверить зависимости и запустить связанные наборы одной командой, например:

   ```bash
   python3 -B scripts/test-manager-fast.py --suite ProxyImportParserTests --suite BrowserRouteProbeTests
   ```

3. Для видимого изменения открыть `./Develop-NeAntik.command --fixture`.
   Не создавать новый bundle на каждую проверку. Не подменять запущенную копию.
4. При интеграции изменений менеджера/общих зависимостей или новом app-кандидате
   выполнить один `--all`, затем необходимые exact release gates. `--all` сначала
   проверяет доступ к списку процессов и loopback TCP/UDP; если среда это запрещает,
   runner возвращает exit75 до SwiftPM и отмечает `testsStarted:false`. Это блокировка
   среды, а не результат тестов. Не повторять запуск в том же ограниченном контексте;
   выполнить его в разрешённой локальной среде. Отдельные
   стенды и документация получают связанные проверки; неизвестные зависимости
   требуют полного прогона. Изменение инструкции не меняет байты приложения.

Полный локальный Python-набор запускается через
`PYTHONDONTWRITEBYTECODE=1 python3 -B scripts/run-python-regression.py`.
Он выполняет ту же проверку до запуска `unittest discover`; при запрете среды
возвращает exit75 с `testsStarted:false`, не создавая Python bytecode в исходниках.

`--list` автоматически получает имена наборов из текущих Swift-файлов.
`--plan` показывает выбор без сборки/Keychain. Неизвестный набор, regex во
входном имени, нулевое число тестов или изменение исходников во время прогона
дают отказ. Кэш тот же, что у локальной manager-сборки; SwiftPM пересобирает
изменённые зависимости. Сами тесты исполняются каждый раз: cached build не
означает cached PASS. Fast tests и Dev build/package используют общую lease физического кэша. Конкурирующая команда получает exit75; SIGTERM/SIGINT отменяют свою child process group и дожидаются settlement. Это координация наших wrappers, не глобальная блокировка всех компиляторов на Mac.

## Что замедляло работу

- Общая Swift-правка автоматически тянула весь Python-набор. Планировщик теперь
  различает пять проверенных общих файлов менеджера: полный Swift сохраняется,
  Python выбирается по зависимостям. Неизвестный source/workflow/runtime по-прежнему
  требует полной проверки. Для Info.plist сокращение возможно только когда
  `--base` подтверждает изменение лишь version/build; одного `--path` недостаточно.
  Изменение выбора не даёт PASS и не заменяет оконные или выпускные проверки.
- Старые suite/full wrappers каждый раз создают временный scratch-каталог и
  удаляют его после теста. Сохраняем их для чистого прогона, а ежедневный цикл
  использует постоянные project-owned caches.
- Ручной список наборов устаревал после появления новых классов. Fast runner
  получает каталог из исходников; пустая выборка не может стать PASS.
- Запуск одной сборки на каждый suite. Несколько `--suite` дают один вызов SwiftPM.
- Нативная проверка повторялась после ошибки только анализатора. Сохранять
  execution receipt и приватный trace до анализа, затем исправлять анализ
  офлайн на тех же байтах с отрицательными контролями.
- Старые pending из накопленного state возвращали закрытые задачи.
  Один CURRENT показывает оставшуюся работу и принятые ограничения.

### Ошибки, устранённые после выпуска 0.8.14

- `-B` родительского Python не действует на Python, который запускают тесты.
  Fast runner передаёт `PYTHONDONTWRITEBYTECODE=1` процессу тестов и его Python-потомкам.
  Проверка использует настоящий импорт в отдельном процессе и отрицательный
  контроль с включённым bytecode; старые source caches не удаляются глобально.
- Анонимный hosted-download использует системный curl, `--disable` первым
  параметром и ограниченный environment. Сырые сетевые stderr не входят в ошибку.
- До дорогих проверок ZIP hosted-helper теперь проверяет форму публичного
  `fingerprint-audit-summary.json`: каноническую schema, channel, дубли ключей
  и ограничение64KiB. Ошибка не выводит содержимое отчёта. Подпись, точная
  привязка private evidence/candidate и проверки архива выполняются полностью.
- В штатный GitHub helper передавать абсолютный путь `--input`/`--body-file`:
  helper устанавливает checkout как рабочий каталог. Пути приватных receipts
  тоже задавать от абсолютного artifact root.
- Оконный exact signed QA следует делать до подписания финального fingerprint
  evidence: оно штатно уничтожает временную authority. Если дополнительная GUI
  проверка действительно нужна позднее, ей нужен отдельный GUI-only manifest
  для тех же байтов и подтверждённое удаление только своего временного ключа.
  Уже пройденный fingerprint-аудит при этом не повторяется.
- Известные resource-исключения согласуются сразу на конкретный ограниченный
  QA-этап и его байты. Нельзя переносить старое одноразовое разрешение на новый
  кандидат; production admission и critical/unknown остаются отдельной защитой.

## Релиз и обновления

- При проверке выбранных source-файлов на секреты сохранять относительные
  пути репозитория в staging/ZIP. Один basename теряет контекст `scripts/tests`
  и может ошибочно трактовать существующий синтетический negative fixture как
  реальные credentials. Исходную диагностику сохранять; scanner не ослаблять.
- Общие файлы доказательств готовит отдельный инструмент
  `scripts/prepare_runtime_common_evidence.py --plan <полный-путь-к-JSON>`.
  Без `--output-directory` он только проверяет входы; с ним создаёт новый
  каталог и отказывается заменять существующий. План содержит `schemaVersion: 1`
  и массив `inputs` из восьми записей `role`, `source` (полный путь), `sha256`.
  Роли: `lock`, `provenance`, `args`, `verification`, `historicalBaseline`,
  `publicationBaseline`, `patchSeries`, `deviceTuples`. Хеши берутся из
  выбранных проверенных входов, а не из непроверенного скачанного описания.
  Два назначения могут ссылаться на один baseline: они не теряются, как в
  словаре с ключом по исходному пути. Все восемь файлов читаются и проверяются
  до создания результата; копируются те же удержанные байты. JSON с повторными
  ключами, ссылки, специальные файлы, пропуски и неверные хеши отклоняются.
  Это только подготовка общих входов: source-proof subtree, нормализация всего
  evidence, подпись и runtime/release gates выполняются отдельно. Инструмент
  не изменяет старые evidence и не даёт `releaseQualified: true`.
- Будущие Direct ZIP-транзакции пишут в stderr строки JSON с
  `kind: neantik.direct-stage`: начало команды, её длительность по monotonic
  clock и результат `exit-zero`, `exit-nonzero` или `runner-error`. Повторные
  проверки разных копий видны как отдельные вызовы. В эти строки входят только
  заранее разрешённые названия этапов; argv, пути, Keychain profile и вывод
  дочерних процессов туда не копируются. Неизвестное название — `unclassified`.
  Это измерение времени, а не новая квитанция допуска или кэш PASS. Все проверки
  выполняются по-прежнему; сбой записи диагностического лога не отменяет их.
  Разбор source-доказательств M156 внутри одного report-checker теперь может
  использовать один [проверенный контекст исходников](SOURCE_VERIFICATION_CONTEXT.md).
  Это не кэш результатов проверки приложения или архива.
- GitHub draft после `gh release create --draft` может иметь `untagged-…` URL:
  запрос `/releases/tags/v…` до публикации вернёт404. Это не доказательство
  отсутствия прав. Найти созданный draft в каталоге releases, сохранить его ID,
  сверить уже загруженные assets через `/releases/{id}` и продолжить публикацию
  этого же draft; не повторять создание, upload или авторизацию.
- Direct doctor — `scripts/preflight-direct-public-release.py`, а не AffPapa
  client. Передавать `--integrated-app`, `--candidate-manifest`,
  `--gui-fingerprint-report`, `--runtime-lock`, `--release-channel public-alpha`,
  точный `--download-url` и `--json`; использовать уже настроенные signing/notary
  environment. До enrollment/fingerprint ожидаемые отсутствующие gates остаются
  blocked: отчёт не заменяет квалификацию нового кандидата.
- Если Python-прогон долго не пишет результаты, сначала подтвердить его live
  handle и собственный PID/cwd, затем снять короткую диагностику. Стек regex не
  доказывает catastrophic backtracking: это может быть повторный обход больших
  доказательств. При подготовке136 диагностирован именно повторный privacy-разбор.
  Строки без обоих видов косой черты не проходят заведомо невозможные path/URL regex;
  проверки секретных полей, глубины, реальных путей и всех proof-проходов сохранены.
  На 58 payload результат совпал с прежним, лексический этап быстрее в 2,4 раза;
  это не измерение полной сборки. [Доказательства](evidence/source-receipt-fastpath-development.json).
  Прерванный полный прогон не считать PASS. Сохранить точный тест из traceback,
  последовательность результатов и source pin; продолжить недостающие тесты,
  отдельно повторив зависимости изменённого checker. Исторические observer hashes
  не переписывать; непостроенный кандидат привязать к новому source commit.
- Обычные model/filesystem unit-тесты не являются нативным app/runtime QA.
  В fixture с собственным shell-stub состояние ресурсов задаётся явно и
  проверяется отдельным pressure-refusal контролем. Реальный браузер, CoreText,
  enrollment и оконные сценарии сохраняют штатный resource gate.
- Подготовительная компиляция/линковка без исполнения приложения или probe —
  build-only. Правило native QA не превращает memory warning в запрет такой
  подготовки. Сохранять прежний output/rollback, один native build, jobs2 и
  отдельный статус unqualified. Реальный браузер, CoreText probe и release QA
  по-прежнему требуют штатного admission или точного разрешённого исключения.
- Перед нативным QA выполнить `python3 -B scripts/native-qa-readiness.py --check`
  в разрешённой macOS-среде. Проверка читает kernel memory pressure и thermal
  state по одному разу, ничего не запускает и не меняет. Exit75 означает
  нехватку ресурсов, exit78 — недоступное наблюдение. Процент свободной памяти
  не заменяет kernel pressure. Не повторять запуск при прежнем условии и не
  отключать защиту; нормальное наблюдение допускает попытку, но не даёт PASS.
- Сначала один законченный срез, затем один source-bound кандидат.
- При смене runtime можно передать `NEANTIK_SOURCE_APP` — канонический путь
  к отдельно аутентифицированному private bundle input. Обязателен
  зарегистрированный `NEANTIK_DIRECT_CANDIDATE_ROOT`; обычные проверки подписи,
  provenance и неизменности вложенного runtime сохраняются. Это вход сборки,
  а не готовый выпуск: старый менеджер внутри такого input не запускается.
  `NEANTIK_UPDATE_LEGACY_APP` указывает на точный предыдущий опубликованный
  app, а не на этот input. Вложенный уже проверенный runtime не переподписывать.
- Если нативный запуск временно запрещён ресурсной защитой, подготовка bundle
  выполняется отдельно: `NEANTIK_MANAGER_PREPARATION_MODE=bundle-only` со
  штатным `prepare-direct-manager-update.sh` и зарегистрированным candidate root.
  Warm cache проверяет актуальность уже скомпилированного менеджера; runtime
  не пересобирается. Подпись, исходники, параметры и inventory запечатываются
  в приватных receipts; `releaseQualified:false`, authority не создаётся.
  Когда ресурсы нормализуются, `zsh scripts/qualify-prepared-manager.sh`
  проверяет те же байты/HEAD и выполняет enrollment без build/copy/sign.
  Незавершённый enrollment не повторяется автоматически. Финальные headed,
  doctor, нотарификация и публичные проверки обязательны по-прежнему.
  Разрабатываемая [диагностика отказов enrollment](ENROLLMENT_FAILURES.md)
  сохраняет исходную причину и результат очистки отдельно. Неопределённый
  результат не разрешает удалять ключ по tag или начинать автоматический повтор.
- Для manager-only обновления с прежним runtime создать зарегистрированный
  каталог командой `python3 -B scripts/release_candidate_location.py
  --project-root "$PWD" --create`. Полученный полный путь передать как
  `NEANTIK_DIRECT_CANDIDATE_ROOT` штатному `Release-NeAntik.command`.
  App, manifest, source binding и отчёт проверки с его подтверждением остаются
  вместе; публичные архивы по-прежнему выходят в `dist`.
  Рабочая `dist/NeAntik.app` сохраняется. Прокси/профили пользователя не нужны
  для QA; exact headed, enrollment, runtime hashes и Direct gates сохраняются.
  Новый путь требует реальной квалификации кандидата перед публикацией.
- Сохранять receipt каждой дорогой стадии: source/build, signed app,
  fingerprint, ZIP, Apple transaction ID, stapling, DMG, hosted bytes, Site.
- Подписанный updater сохраняет предыдущую primary-пару модулей без
  переподписи. Для подготовки кандидата передать `NEANTIK_UPDATE_LEGACY_APP`
  с точным предыдущим квалифицированным приложением. Packaging проверяет его
  подпись, фиксированный сертификат, signed pins и неизменность файлов через
  native проверки; текущая пара размещается в `Helpers/v2`. Обязательная
  continuity policy отказывает при пропуске входа. Новый runtime не нужен.
  Изменение модулей требует настоящего native install/rollback, а не только
  проверки архива. Старые публичные архивы не заменять.
- Сбой локального продолжения после Apple Accepted не требует новой отправки:
  `notarize_direct_transaction.py` уже поддерживает проверенное продолжение
  известной транзакции. Использовать существующий ZIP-transaction workflow.
- DMG сохраняет собственную транзакцию в `dist/private/dmg-transactions`.
  Скрипт выводит её путь до отправки. После прерывания использовать
  `./scripts/release-direct-dmg.sh --resume <полный-путь-транзакции>`.
  Это продолжение известного Apple ID: ZIP, сборка, подпись исходного образа
  и отправка не повторяются. Нужны тот же source/policy и кандидат.
  Если отправка могла произойти, но ID не сохранился, скрипт отказывает:
  сначала выяснить результат в Apple, а не создавать новую отправку.
  Обычная повторная команда также замечает сохранённую транзакцию до упаковки.
- Submitted DMG неизменяемый; stapling выполняется на отдельной копии.
  Прерванный stapling восстанавливает только эту ещё не опубликованную копию.
  Финальные native проверки, точный ZIP/app content, candidate manifest,
  подпись, Gatekeeper, privacy, hash и запрет overwrite сохраняются.
  Fault tests подтверждают локальную логику; реальная qualification нового
  пути нотарификации требуется на следующем точном кандидате.
- Не заменять опубликованные assets и не выпускать app заново ради поправки
  разработческих команд. GitHub/Site публикация должна следовать реальным байтам.

## Проверенный пример

13 октября 2026: два выбранных набора, **30 тестов / 2 suites**, cached native
build + исполнение заняли **0,712 с** на текущем Mac. Проверка актуальности
QA-менеджера: native build **0,28 с**. Это отдельные измерения тёплого кэша,
не обещание такой скорости clean build, полного suite или notarization.
Jobs остаются2: это ограничение нагрузки, не исправление причины kernel panic.

Подробный лог/receipt хранится локально в `.build/neantik-local/test-receipts`;
обычный вывод содержит короткий итог, не весь compiler/test transcript.
Публичная команда не читает секреты и не запускает signing/notarization/deploy.

Итог Swift Testing включает отключённые тесты. Receipts отдельно показывают
строки реально прошедших и пропущенных тестов; вывод только со skipped-тестами
отклоняется. Benchmark импорта5000 профилей сохраняет прежние count/time
assertions и требует inherited NOFILE и kern.maxfilesperproc>=16024. Если
ёмкость меньше или не удалось её прочитать, benchmark явно пропускается;
системные лимиты для него не повышаются. Такой CI не
подтверждает производительность этого benchmark — нужен отдельный реальный
проход на машине с достаточной ёмкостью.

## CI и выбор проверок

- Resolver проверяет реальный импорт и typecheck публичных SDK API менеджера
  для ARM64/macOS14, Swift5 language mode, compiler не ниже Swift6.2.
  Различие build-номеров compiler и SDK само по себе допустимо при module
  stability. Explicit DEVELOPER_DIR не заменяется другой установкой при отказе.
  Probe не линкует и не запускает приложение; полный build/tests остаются
  отдельными проверками. Проверка локально занимает около3с, поэтому это
  дополнительное время к ранее измеренному тёплому native run.
  Каждый typecheck имеет срок60с и собственный временный module cache;
  после отмены supervisor завершает свою process group до освобождения lease.
- `workflow_dispatch` с `toolchain_probe=true` выполняет только эту диагностику.
  Она не означает PASS тестов приложения и позволяет исправить setup до
  повторного запуска четырёх сборочных групп.
- Четыре чистых CI shards вместо148сборочных jobs. Каждый shard строит общий target в собственном cache и запускает suites последовательными отдельными процессами. Между CI jobs/runs кэш не переносится. Native execution обоих labels и code paths не заменяется Python mock.
- Каталог следует реальным типам Swift, включая несколько suites в одном файле и extensions существующей suite. Вложенные файлы включены. Неподдержанная unscoped @Test declaration даёт отказ; wholly opt-in и Live suites исключены из обычного CI. Mixed QA flags/data-root overrides удаляются из child environment.
- Plan-manager-checks показывает команды и дополнительные gates, но ничего не запускает. Rename/delete/untracked входят в diff; неизвестные/shared inputs требуют full regression. Карта рекомендаций не заменяет анализ зависимостей.
- Workflow changes проверяются targeted Python contracts и одним достаточным реальным native integration. Новая сборка приложения не нужна для правки instructions/check planner.
- После завершения среза записать в CURRENT один следующий шаг; накопленный state остаётся историей. Большие manifests читать по нужным полям.

## Правила для процесса агента

Перед дорогой операцией CURRENT должен отвечать на четыре вопроса: что изменено,
что считается завершением, какой receipt уже есть и почему нужен повтор.
Проверять существование файла/набора и возможности среды до запуска. После
сбоя сначала определить класс: продукт, стенд, настройка или внешняя среда.
Ошибка анализатора исправляется на сохранённых данных; новый браузер нужен
при изменении его входов или неполном наблюдении. Два одинаковых сбоя запрещают
ещё один слепой повтор. Новый способ входа нужен лишь после отказа конкретной
необходимой операции через уже рабочий маршрут.

Не подключать skill/MCP ради количества. Project implementation workflow находится в `.agents/skills/neantik-development/SKILL.md`; runtime audit загружается только для нужного runtime scope. AGENTS хранит короткие неизменные границы, workflow — skill/scripts, история — receipts/memory router. API cache knobs не являются настройками desktop; модель, reasoning, permissions и credential scope не меняются ради недоказанного ускорения.

## Сетевые проверки без ручных гонок

`scripts/runtime-network/manager-route-fixture.py` принимает текущий подписанный
app и manifest, проверяет байты и подпись, создаёт два временных профиля и
запускает менеджер в существующем authenticated audit режиме. Пароль стенда
тестовый; GUI хранит его только в audit backend. Отдельный MCP используется
лишь для создания metadata: его процесс не наследует этот Keychain backend.

- Создать файл `arm-cut-on-stream` в **принадлежащем этому запуску** audit root
  перед открытием `proxy-success`. Стенд оборвёт соединения после первой
  отправленной порции данных защищённого потока. Direct-поток его не активирует.
  Это устраняет гонку ручного клика с завершением потока; сам поток ограничен180с.
- `finish-fixture` завершает supervisor. При закрытии/deadline он проверяет
  UID, точный runtime, отдельный user-data-dir и mock Keychain перед SIGTERM
  оставшегося своего браузера. Ошибка проверки процесса остаётся ограничением.
  Такой cleanup не доказывает штатное сохранение cookies или graceful close.
- Нативные наблюдения сохранять отдельно от серверных счётчиков. Для повторного
  анализа сохранённых receipts использовать
  `python3 -B scripts/runtime-network/analyze-manager-route.py --receipts <directory>`.
  Он проверяет порядок событий, реальный активный обрыв, отсутствие обращений
  к origin во время отказа, восстановление и Direct-контроль того же endpoint.
  Пропущенный receipt, противоречие, пустой ledger или слабый контроль дают FAIL.
  Вывод содержит хеши входов и анализатора; это ограниченное HTTP/TCP наблюдение,
  без квалификации DNS, TLS upstream, WebRTC и всего релиза.
- GUI-инструмент может переключиться на другой процесс с тем же bundle ID.
  Перед каждым действием после повторного выбора проверить собственный PID/root
  и получить AX без вывода. Если маркеры двух QA-профилей отсутствуют — прекратить
  действия. После Quit проверить PID; не искать приложение заново по bundle ID.

HTTPS проверяется отдельно через opt-in `--owned-https`: нормальная проверка
сертификата браузером, фиксированный endpoint browser.free, свежий nonce и
ответ с проверенной Ed25519-подписью. Нужны связанный PID/runtime, CONNECT до
подписанного ответа, отсутствие ответа при отказе upstream, намеренный Direct
к тому же endpoint во время отказа и восстановление исходной сессии. Старый
HTTP-анализатор этих условий не проверяет. HTTPS destination через HTTP proxy
не является проверкой TLS к HTTPS upstream или DNS на проводе.
Один явно созданный audit authority используется с тем же точным app/manifest
до потребления или штатного удаления; каждый повтор fixture не создаёт ключ.
Запуск, подпись ответа, закрытие процессов и удаление authority — разные этапы.

### Удаление временного audit authority

Отдельный внутренний режим `--neantik-retire-fingerprint-evidence` удаляет
только временную authority выбранного QA-manifest. Он выполнен на точной
скачанной0.8.21 после [physical-TCP проверки](evidence/manager-tcp-0.8.21.json).
Это не разрешает удалять произвольные ключи и не заменяет квалификацию
изменённой команды или нового кандидата.

Команда принимает `--candidate-app` (точное прежнее или текущее `NeAntik.app`),
`--candidate-manifest` и `--output` с именем `fingerprint-retirement.json`
в собственном каталоге с правами0700. Перед запуском закончить принадлежащие
этому аудиту процессы и сохранить их receipts. Обычный fingerprint-аудит
ради очистки не повторять.

- Проверяются настоящая identity вызывающего процесса, фиксированный
  Developer ID/certificate, подписанный кандидат и полный manifest inventory.
- Ключ должен совпасть с manifest и подписать отдельное разрешение удаления.
  Оно сохраняется как `fingerprint-retirement.intent.json` до удаления.
- Затем проверяются отсутствие самого ключа и его reservation. Только после
  этого пишется отдельная квитанция очистки с `releaseQualified:false`.
- При сбое сохранить каталог. Повтор использует подписанный intent и проверяет
  итог заново; не создаёт ключ и не подписывает release report. Уже записанная
  идентичная квитанция допускает сверку после ошибки directory fsync.
- Ошибка или чужой surviving key дают отказ. Нельзя передать произвольный
  session ID, Keychain service/tag или вызвать операцию через MCP.

Это работа с временным ключом release-аудита, без открытия ProfileStore,
BrowserData, сохранённых паролей или браузерных окон. Unit controls проверяют
логику; настоящие Security.framework/Keychain и подписанные байты проверяются
отдельно до включения режима в квалифицированный выпуск.

Изолированные stdlib harnesses перечислены явно в check planner и выбирают
свои тесты вместо всего Python suite. Неизвестный скрипт сохраняет полный прогон.
Изменение анализатора проверять на сохранённом trace; изменение самого стенда
требует его настоящих loopback controls и новой нативной проверки при следующей
квалификации. Старый нативный результат не становится результатом нового стенда.

### Повтор DMG qualification

Настоящая DMG transaction уже выполнена для опубликованных артефактов;
результат относится к их точным байтам и входам. Повтор нужен при новом
кандидате или изменении DMG-driver. Сохранённая транзакция продолжается без
второй отправки; публичные байты квалифицируются отдельно. Локальные fault
tests не заменяют native gate. Полный release pipeline не повторяется ради
диагностики одной завершённой стадии.

### Результат нативной проверки DMG и быстрый отказ

0.8.5 завершила настоящую DMG transaction: Apple Accepted, stapling,
Gatekeeper и публичные байты проверены. Повторная отправка не нужна.
`--check-new` дополнительно проверяет source receipt до дорогой распаковки
и hdiutil. При executable Python cache рядом с исходниками он отказывает
заранее; ничего не удаляет. `start()` повторно фиксирует source, чтобы
предварительная проверка не заменила конечную привязку.
Disposable DeviceMemory harness использует explicit mock Keychain и
allowlisted environment; временный HOME сам по себе не изолирует Keychain.

### Среда тестов и fixture-каталог

Полный Swift-прогон включает собственные kernel-process и loopback/Unix-socket controls. В ограниченной среде заранее выбрать разрешённый QA execution context; Permission denied не исправляется ослаблением assertions. Если ограничения обнаружены в первом прогоне, сохранить его как setup failure и повторить только упавшие наборы с тем же input digest. Не объявлять первоначальный прогон зелёным.

Каталог opt-in fixtures перечисляет необходимые environment inputs, включая URLs/roots; не каждый input является boolean enable-флагом. Проверять декларации реальных suite types, поскольку несколько suites могут находиться в одном файле. Каждая @Test в чисто opt-in suite должна иметь явный enabled guard; нулевой или только skipped результат остаётся отказом runner.

### Фоновая сеть: отдельный режим измерения

Старый DEBUG relay NetLog-стенд отключает background networking, component
update, sync и extensions. Его пустой лог не доказывает отсутствие фоновых
запросов при обычном запуске. `observeBackgroundNetworking` работает только
в отдельной signed DEBUG QA.app с приватным root и обычным manager launch.
Он добавляет mock Keychain, Default NetLog и отдельный ephemeral loopback CDP
для ограниченного observer скачиваний. Обычный bundle не включает этот режим.
Ранние failure/restart эксперименты и route probe в нём отклоняются.
Attachment endpoint открывается только после ACK `Browser.setDownloadBehavior`
с owned-папкой: user preferences недостаточны из-за managed DownloadDirectory.
Observer разрешает лишь настройку/отмену download и две фиксированные owned
navigation; произвольного JS/evaluate нет. Завершение и отмена проверяют реальные
события браузера и байты файла. Никакие production preferences не меняются.

`observe_background_attempts` в `controlled-browser-route-observer.py` выдаёт
только счётчики и выбранные маршруты, включая missing/other/Direct. Redirect
legs не заимствуют выбор маршрута друг у друга. Категория адреса не доказывает
назначение запроса; выбор proxy не доказывает успешный socket, отсутствие DNS
на проводе или общую приватность. Полный trace сохраняется приватно, публичный
отчёт не содержит URL, headers, proxy address или сырые IP. Для изменения
анализатора достаточно его двух наборов контролей и повторного анализа уже
завершённого trace; новый запуск нужен при изменении browser/fixture inputs.

Production-ID QA нельзя выбирать через CUA getApp по имени/пути: LaunchServices
может активировать обычное окно с тем же ID. Использовать отдельный QA ID либо
PID/generation/lease-bound native operations. Завершение процесса проверять
напрямую; повторное getApp может открыть приложение снова.
