# NeAntik Chromium + WebKit implementation plan

Base: published source `8ceaf9077f9b77dff885ea866e8fb101dfa93056`. Work in a separate development checkout with new synthetic profile IDs. The published 0.9.6 artifacts, rollback and existing profile data are fixed inputs. Record actual evidence in CURRENT and dated receipts.

## Architecture

- The manager owns profile metadata, identity settings, revision, leases and a route policy. Chromium retains its existing bundled runtime and controls. WebKit chooses between macOS WebKit for explicit Direct profiles and the signed owned host for profiles that require an isolated proxy. The manager rejects any unsupported combination before acquiring a lease, resolving credentials or starting a view. No runtime or storage fallback.
- The system-WebKit path uses the persistent UUID store and the native OS identity. Keep the existing store IDs. Keep the owned profile's store and process identity separate. Restart or failure must preserve explicit engine, route and revision. Capabilities reported by GUI and MCP describe support separately from an observed live route.
- The owned WebKit host verifies its exact loaded runtime, profile lease handoff and Networking XPC identity. Its outgoing network boundary permits only the profile's authorized broker. The broker owns upstream TLS/CONNECT or SOCKS5, name resolution policy, revocation and upstream credentials. Check the boundary at the Networking process, not just in WKWebsiteDataStore.
- Support explicit WebRTC policies. Native disable must close peer connections and data-channel APIs before the first page, or refuse the protected launch. Media permission is separate. Relay-only may be added only after a real controlled TURN session proves the advertised candidate and traffic route match and no direct UDP path survives. Do not fake candidate IP strings. Never apply Chromium fingerprint injection to WebKit.
- Qualify each proposed WebKit identity parameter independently. Start with native coherent WebKit identity; offer an override only if the engine can apply it consistently to HTTP, documents, frames and workers as applicable, and A→B→A proves persistence and separation. Preserve unavailable settings and expose the reason. Avoid claiming anonymity or indistinguishability.
