1. The patched script can return 0 when all known pinned source/toolchain inputs are present; its own report still leaves `completeBuildInputsEstablished`, `recipientRelinkProved`, and `licenseOrSourceOfferQualified` false.
2. Extract the pinned WebKit and NeAntik source archives; check and apply the pinned patch. Configure and build the 14 targets from the draft recipe in a fresh directory. The recipient must supply compatible Xcode 27.0/macOS SDK 27.0, CMake, Ninja, Swift, and remaining transitive build inputs; their portability is still open.
3. Stage the built runtime using `stage-webkit-runtime.py --upstream-source <extracted-WebKit> --manifest <extracted-NeAntik>/runtime/webkit-production-staging-v4.json <build-root> <new-Frameworks>`. This only copies the runtime; it does not sign or qualify it. Schema 4 has pinned network-sandbox and Swift CompatibilitySpan inputs; any replacement build that changes these pins must be reviewed and rebound rather than silently accepted.
4. Build the NeAntik manager and standalone host from the same source snapshot with the intended owned-WebKit feature selection. `build-webkit-standalone-host.py --configuration release --production-proxy` builds a host but explicitly returns `built-production-mode-unqualified`; it does not produce a release by itself. The manager build/sign procedure and its dependency closure still need a complete portable recipe.
5. Sign a **disposable manager copy** with the recipient's existing Developer ID Application identity. Run `resign-webkit-recipient-runtime.py --manager-app <recipient-signed-manager.app> --source-frameworks <new-Frameworks> --output-frameworks <new-signed-Frameworks> --identity <same-team-identity>`. The script copies and atomically publishes a separately signed runtime, verifies Mach-O images, XPC entitlements, team, timestamp, and RPATHs. It rejects ad-hoc signing, another team, or an existing output path.
6. On a separate disposable manager copy, run `package-webkit-host.py --app <recipient-signed-manager-copy.app> --host-binary <built-NeAntikWebKitHost> --runtime-frameworks <new-signed-Frameworks> --identity <same-team-identity> --recipient-relink`. The recipient flag takes the signed manager's team; the public publisher route remains fixed to NeAntik's team. Verify the resulting host pin and outer app signature before any launch. This route has not been exercised end-to-end by an independent recipient.

The publisher-signed app cannot be modified and re-signed by a recipient who lacks the publisher identity. A recipient instead signs an independently built manager copy with their own Developer ID Application identity. Whether that requirement provides adequate practical LGPL replacement ability remains an open release review item; this note does not make a legal determination.
